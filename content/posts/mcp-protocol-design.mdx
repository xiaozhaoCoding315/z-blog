工具调用一开始是没有标准的。

每家模型厂商有自己的 JSON schema，每个 Agent 框架有自己的抽象层，每个 SaaS 有自己的 API。想让 Claude 读你的 Notion、让 GPT 读你的数据库，就得写两套适配。

MCP（Model Context Protocol）做的事情很朴素：**定义一个统一的接口，让「模型侧」和「数据源侧」各自只实现一次。**

## 问题本来是 N×M

假设有 5 个模型客户端、10 个数据源。没有标准时，你要写 5×10 = 50 个适配器。

有了标准，客户端实现一次协议，数据源实现一次协议，总共 5+10 = 15 个。

这不是什么高深的数学，但它是**协议存在的唯一理由**。USB、LSP、OpenAPI 都遵循同一个逻辑：把组合爆炸压成加法。

LSP 是最好的类比。编辑器不再为每种语言写一套补全逻辑，语言服务器不再为每个编辑器写一套协议实现。MCP 想做的是同一件事，只是对象从「编辑器 ↔ 语言」换成了「模型 ↔ 工具」。

## 它站在哪一侧

MCP 的架构里有两个角色：

| 角色 | 职责 | 典型实现 |
| --- | --- | --- |
| Host / Client | 发起请求、管理连接、决定要不要调用 | Claude Desktop、IDE、自建 Agent |
| Server | 暴露能力（tools / resources / prompts） | 一个包装了数据库的进程 |

关键在于：**协议是客户端驱动的，不是服务端驱动的。**

这意味着你的博客、你的数据库、你的文件系统都可以是一个 MCP Server，而「要不要让模型访问它」这个决定权在客户端手里。服务端只负责声明「我能做什么」，不负责「谁会来用」。

这个设计选择很重要。它让权限边界落在用户能控制的地方——你在客户端里勾选允许哪些 server，而不是每个 server 各自搞一套鉴权。

## 三种能力，别混为一谈

MCP 暴露的不是只有「工具」：

**Tools** —— 模型可以调用的函数。有副作用，需要确认。查数据库、发消息、写文件都属于这一类。

**Resources** —— 只读的数据。像文件、文档、日志。模型可以把它们读进上下文。

**Prompts** —— 预设的提示模板。用户主动触发，不是模型自己决定用。

这个划分是有意义的。它区分了「模型自己决定要不要做」（tools，通常要人工确认）、「模型按需读取」（resources，只读所以风险低）、「用户明确要求」（prompts）。

很多实现只做了 tools，然后发现所有东西都得走「调用」这一条路，连读个文件都要一次 tool call。其实读文件应该是 resource。

## 传输层：stdio 与 HTTP

协议本身是 JSON-RPC 2.0。传输有两种常见形态：

**stdio** —— server 作为子进程启动，通过标准输入输出通信。适合本地工具，比如文件系统、本地数据库。没有网络暴露，权限天然受限。

**HTTP + SSE** —— 远程 server。这里有个细节：早期的规范用的是「HTTP POST 上行 + SSE 下行」的双通道模式，后来改成了 Streamable HTTP，把两条通道合并到一个端点。

为什么值得改？因为双通道在网关、代理、负载均衡面前很麻烦。你需要保证两条连接落到同一台后端，否则状态对不上。单端点解决了这个问题。

## 一个最小的 server 长什么样

```python
from mcp.server import Server
import mcp.types as types

server = Server("blog-tools")

@server.list_tools()
async def list_tools():
    return [
        types.Tool(
            name="search_posts",
            description="按关键词搜索博客文章，返回标题和链接",
            inputSchema={
                "type": "object",
                "properties": {
                    "query": {"type": "string", "description": "搜索词"}
                },
                "required": ["query"],
            },
        )
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict):
    if name == "search_posts":
        results = await do_search(arguments["query"])
        return [types.TextContent(type="text", text=format(results))]
```

核心就三件事：声明能力（`list_tools`）、执行调用（`call_tool`）、返回结构化结果。

<Callout type="tip" title="description 是最重要的字段">

工具能不能被正确调用，八成取决于 `description` 写得清不清楚。模型看不到你的实现，只看这段文字。写「搜索文章」和写「按关键词搜索博客文章，返回标题和链接，不支持正则」，后者被正确调用的概率高得多。

这也是为什么很多人抱怨「模型不调用我的工具」——往往是描述太模糊，或者参数 schema 没写 `required`，模型不知道该传什么。

</Callout>

## 我为什么暂时没在博客里接 MCP

想清楚了才没做。MCP 的价值在「多个客户端复用同一个 server」。这个博客的 AI 助手只有一个客户端，工具只有一个（站内检索），直接写一个函数就够了。

**引入协议的成本是：多一层抽象、多一个进程、多一套错误处理。** 收益是：别的客户端（比如用户自己的 Claude Desktop）也能用。

后者确实有价值——但它是个「将来可能有」的收益，不是现在的痛点。所以我把它记在待办里，而不是现在实现。

判断要不要用 MCP，我觉得就一条：**你的工具会不会被不止一个客户端调用。** 会，就值得；不会，一个普通函数更简单。

## 协议解决不了的事

最后提醒一句，MCP 标准化的是**通信**，不是**安全性**。

- 它不保证 server 的实现是安全的
- 它不决定哪些工具该被自动调用
- 它不处理「模型被诱导调用了危险工具」这类问题

这些依然是你的责任。协议让连接变容易，也让「连上了一个不该连的东西」变容易。
