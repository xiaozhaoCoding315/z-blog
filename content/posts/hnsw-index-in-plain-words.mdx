pgvector 里建索引时，你会看到这几个参数：

```sql
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

`m` 和 `ef_construction` 是什么意思？为什么改了它们召回率会变？

这篇用尽量少的数学讲清楚 HNSW 在干什么。

## 暴力搜索的问题

给定一个查询向量，找出最相似的 k 个，最直接的办法是**算它和每一个向量的距离，然后排序**。

这就是精确搜索。100 万条向量、每条 1024 维，一次查询要算 100 万次距离，每次 1024 次乘加。即使是 SIMD 优化过的实现，也是几十毫秒起步。数据量再涨一个数量级，就没法用了。

向量索引要解决的就是：**怎么不算这么多，还能找到差不多对的结果。**

## 小世界图

HNSW 的第一层思想叫「可导航小世界图」（Navigable Small World）。

把每个向量看成一个点，每个点连几条边到「离它比较近的其他点」。检索时从某个入口点出发，沿着边走向「离查询向量更近」的方向，直到周围的点都不比当前点更近为止。

这就像在一个城市里找最近的超市：你不需要知道所有超市的位置，只要沿着街道走，每次走向看起来更近的方向。

问题在于：如果图只连「最近的邻居」，图会变成一堆互不相连的孤岛。从一个岛走到不了另一个岛。

所以 HNSW 的第二层思想是**分层**。

## 分层：像地铁线路图

HNSW 构建多层图：

- 最底层（第 0 层）包含所有点，每个点连 `m` 个近邻
- 上一层是下层的「采样」，点更少、边更长
- 最顶层只有很少的点，边跨度很大

检索时从顶层开始，找到局部最近的点，然后**下沉到下一层**，以这个点为入口继续找。逐层下沉，最后在底层做精细搜索。

![HNSW 的分层图结构：顶层稀疏、边跨度大，逐层下沉到底层做精细搜索](/images/diagrams/hnsw-layers.svg)

这很像地铁：先坐大站快线跨越城市，再换乘普通线路，最后步行到目的地。每一层负责不同尺度的「跳跃」。

## 那几个参数在控制什么

**`m`（每层每个点的最大连接数）**

连得多，图更连通，召回更好，但内存和构建时间都上去了。默认 16 是个比较平衡的值。数据量大、维度高的时候可以调到 32 或 48。

**`ef_construction`（构建时候选邻居的数量）**

构建每个点时，候选池有多大。候选池越大，选出来的邻居质量越高，图的连通性越好。默认 64。调到 200 会让构建慢很多，但召回通常能提升几个点。

**`ef_search`（查询时候选池的大小）** —— 这个在 pgvector 里通过 `hnsw.ef_search` 设置

查询时维护一个大小为 `ef_search` 的候选集，走完整个搜索后从中取 top-k。这个参数**运行时可以调**，是最重要的调优旋钮：

```sql
SET LOCAL hnsw.ef_search = 40;   -- 默认 40
```

调大 → 召回率上升，查询变慢。调小 → 变快，可能漏。

<Callout type="tip" title="怎么调 ef_search">

拿一批真实查询跑一遍，记录「精确搜索的结果」和「HNSW 的结果」的重合度（这就是 Recall@k）。然后从 40 开始，往上调到召回率达到你需要的水平（比如 0.95），记下那个值。

不要凭感觉设。这个参数直接决定你花多少钱、用户搜不搜得到东西。

</Callout>

## 它为什么是「近似」的

HNSW 有两个固有的近似来源：

**1. 图不是全连通的。** 理论上存在某些点，从入口走不到。虽然分层大幅降低了概率，但不是零。

**2. 贪心会走进死胡同。** 每一层都是「沿最近的边前进」，如果最近的边指向一个局部最优但全局不是最优的区域，就出不来了。

这也是为什么**召回率永远不可能 100%**（除非 `ef_search` 大到退化成暴力搜索）。

工程上接受这个取舍，是因为：从 99.9% 召回降到 95%，查询速度可能快 100 倍。而 95% 召回对大多数应用（搜索、推荐、RAG）已经足够。

## 什么时候不该用 HNSW

**数据量小。** 十万条以下，暴力搜索完全够用，索引反而是负担（构建慢、占内存）。

**需要精确结果。** 比如去重、找完全相同的向量，这时候近似搜索会漏。

**内存紧张。** HNSW 索引本身要占内存，大概是原始向量数据的 1.5 到 2 倍（因为要存图结构）。2G 内存的服务器上，pgvector 的 HNSW 索引很容易把内存吃满。

替代方案是 IVF 系列（倒排文件）：先聚类，查询时只扫最近的几个簇。内存占用小，但召回对聚类质量敏感。pgvector 也支持 `ivfflat`。

## 我在博客里的实际情况

这个博客的分块数量在几百到几千的量级。这个规模下，**HNSW 的收益其实不大**——暴力搜索也就几毫秒。

我还是建了索引，原因是：

1. 建索引不花什么成本（构建时几秒）
2. 文章数会涨，提前建好省得以后改
3. pgvector 在有索引时仍然会自动选择用不用（优化器会判断）

但如果让我在一个只有几十条数据的场景里建 HNSW，我会说别折腾——先量一下暴力搜索的耗时，很多时候它根本不是你想象的瓶颈。

**先测，再优化。** 这句话在向量检索上尤其适用，因为「近似」带来的召回损失是隐性成本，不会在延迟数字里体现出来。
