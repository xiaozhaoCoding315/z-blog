「给 Agent 加长期记忆」听起来像是个很酷的功能：Agent 记得你上次说过什么，记得你的偏好，记得三个月前的对话。

真做起来，最常见的结局是：塞了一堆对话进向量库，检索出来的全是无关的碎片，反而污染了上下文。

问题不在检索技术，在**没有区分记忆的类型**。

## 记忆其实有三种

按「怎么存、怎么取」来分：

| 类型 | 内容 | 存储 | 检索方式 |
| --- | --- | --- | --- |
| 工作记忆 | 当前任务的状态 | 上下文窗口 / 会话变量 | 直接读，不需要检索 |
| 情节记忆 | 发生过什么（某次对话、某次操作） | 按时间序列存 | 按时间或主题检索 |
| 语义记忆 | 关于用户/世界的稳定事实 | 结构化键值 | 按 key 精确读 |

把这三类混在一个向量库里，是大多数「记忆系统」失败的原因。

## 工作记忆：就是上下文本身

这一类根本不需要「记忆系统」。它就是当前的 messages 数组、当前的计划、当前的中间结果。

需要做的只是**管理它的长度**：

- 老的对话轮次摘要成一段
- 工具返回的长结果只保留结论
- 中间产物（比如检索到的文档）用完就丢

这部分做好了，Agent 的表现提升比任何「长期记忆」都大。我见过很多项目，上下文管理一团糟，却去搞向量记忆——方向错了。

## 情节记忆：按时间检索，不是按相似度

「上次我们讨论的那个部署问题」——这是情节记忆。

它和语义记忆最大的区别是：**它的价值在于时序，不在于语义相似。**

如果你把每次对话总结成一段话塞进向量库，然后按相似度检索，会出现两个问题：

**1. 检索到的永远是「最像的那次」，而不是「最近的那次」。**

用户说「继续上次的」，他指的是时间上最近的那次，不是语义最像的那次。

**2. 摘要丢掉了可操作性。**

「讨论了部署问题」这条摘要，对当前任务几乎没有帮助。有用的信息是「上次结论是：不要在 2G 机器上构建镜像」，这是一个**结论**，不是一次**事件**。

所以情节记忆的存储应该带明确的时间戳和任务标签，检索时**先用时间过滤，再用语义排序**：

```sql
SELECT summary, created_at
FROM episodes
WHERE user_id = $1
  AND created_at > now() - interval '30 days'
ORDER BY embedding <=> $2
LIMIT 3;
```

先按时间圈定范围，再在里面找相关的。顺序反过来，结果基本没用。

## 语义记忆：结构化，不用向量

「用户偏好 Python 而不是 Java」「用户的时区是 UTC+8」——这是语义记忆。

这类信息的特征是：**key 是明确的，值会变。**

用向量检索去找「用户用什么语言」，是在用模糊工具解决精确问题。正确做法是一张表：

```sql
CREATE TABLE user_facts (
  user_id   text NOT NULL,
  key       text NOT NULL,
  value     jsonb NOT NULL,
  confidence real NOT NULL DEFAULT 1.0,
  updated_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, key)
);
```

读取时按 key 直接取，几毫秒。写入时 upsert，带一个 `confidence` 字段——因为从对话里推断出来的事实不一定可靠。

<Callout type="tip" title="怎么从对话里提取事实">

不要让模型「自由地记录一切」，那会写进一堆噪音。

给一个固定的 key 集合，让模型做分类判断：

```
从这轮对话里提取用户偏好，只能填这些 key：
- language（编程语言偏好）
- timezone
- response_style（简洁/详细）
- tech_stack（数组）
不确定的不要填。
```

固定的 key 集合，让记忆变成可控的写入，而不是无限的膨胀。

</Callout>

## 什么时候该「忘记」

记忆系统最容易忽略的部分。

**过期。** 情节记忆应该有保留期（比如 90 天）。超过就删——不是压缩，是删。老的对话摘要对当前任务的价值接近零，但检索时它们会占位。

**冲突。** 同一个 key 的新值应该覆盖旧值，而不是并存。如果并存，模型会看到两个矛盾的事实，然后困惑。

**低置信度。** 从对话推断出来的事实，如果 confidence 低于阈值，不要注入上下文。宁可没有记忆，也不要错误的记忆。

**衰减。** 我用的一个简单规则：`score = confidence × 0.5^(days/30)`。30 天减半。检索时按这个分数排序，太老或太不确定的自然排到后面。

## 上下文注入的预算

这是最实际的约束：**上下文窗口有限，记忆和检索结果都在抢位置。**

我的分配大致是：

- 系统提示：固定，不超过 10%
- 记忆（语义 + 情节）：不超过 15%
- 检索到的文档：不超过 40%
- 对话历史：剩下的
- 留给输出：至少 20%

超出预算就按分数截断。**不要因为「可能有用的都塞进去」** ——上下文里塞了无关信息，模型的表现会下降，这一点在长上下文模型上依然成立。

## 一个反直觉的结论

做了几轮之后，我的结论是：**大多数 Agent 不需要「长期记忆」。**

需要的是：

1. 好的上下文压缩（工作记忆）
2. 一个能按 key 读的用户偏好表（语义记忆，几十行代码）
3. 一个能查最近任务记录的日志（情节记忆，可能就是一张普通表）

向量库只有在「记忆条目上千、且确实需要模糊匹配」时才值得上。在那之前，它带来的是复杂度，不是能力。
