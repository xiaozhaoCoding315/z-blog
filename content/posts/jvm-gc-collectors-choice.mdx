「用 ZGC 吧，它停顿最短。」

这句话没错，但没回答问题。真正的问题是：**你的应用需要多短的停顿？**

不需要 1 毫秒停顿的应用，上 ZGC 是在为用不上的能力付代价（更高的 CPU 开销、更少的调优经验积累）。

## 三个指标

选 GC 只看三件事：

| 指标 | 含义 | 影响 |
| --- | --- | --- |
| 停顿时间 | 单次 STW 的最长时长 | 影响延迟 SLO |
| 吞吐量 | 应用线程占 CPU 的比例 | 影响单位成本 |
| 堆内存开销 | GC 自身需要的额外内存 | 影响部署密度 |

**这三个指标互相冲突。** 停顿越短，通常要付出越多的 CPU 和内存。

## 各收集器在哪个位置

**Serial**：单线程，停顿长（秒级），内存开销最小。适合极小堆（几百 MB）或者单核环境。

**Parallel**：多线程，停顿较长（百毫秒到秒），吞吐量最高。适合批处理、离线计算——这类场景不在乎停顿，只在乎总时间。

**G1**：分区域收集，可设停顿目标（`MaxGCPauseMillis`，默认 200ms）。它会在「停顿预算」和「吞吐」之间做权衡。JDK 9 之后的默认选择。

**ZGC**：并发标记 + 并发整理，停顿通常在 1ms 以内，且与堆大小基本无关（堆从 1G 到 1T，停顿差别不大）。代价是 CPU 开销更高（需要并发线程），以及一些场景下的吞吐损失。

**Shenandoah**：思路和 ZGC 类似（并发整理），停顿与堆大小无关。在 OpenJDK 里可用，某些发行版默认不包含。

<Callout type="info" title="G1 的停顿目标不是保证">

`MaxGCPauseMillis=200` 是一个**目标**，不是承诺。G1 会尽力达成，但在堆快满、对象存活率高的时候，它会放弃目标去做一次 Full GC——那可能是秒级停顿。

所以设了目标之后，一定要监控实际的停顿分布（P99、最大值），而不是相信配置。

</Callout>

## 怎么定停顿预算

从 SLO 反推，而不是从 GC 参数正推。

假设接口 P99 要求 100ms，那么：

- GC 停顿必须远小于 100ms，否则一次 GC 就能让 P99 爆掉
- 保守起见，取 SLO 的 1/10：**停顿预算 10ms**

再考虑频率：如果堆 8G、分配速率 2G/s，G1 可能每分钟触发多次 Young GC。每次 50ms 停顿，一分钟就是几百毫秒的停顿时长——对高 QPS 的服务，这会体现在吞吐上。

所以真正的公式是：

```
停顿预算 × 频率 = 每秒损失的 CPU 时间
```

单次停顿短但频繁，和单次停顿长但稀少，对吞吐的影响可能一样。

## 各场景的实际选择

**Web API（延迟敏感，堆 4–16G）**：G1 足够。把 `MaxGCPauseMillis` 设到能接受的级别（比如 50ms），监控实际停顿。只有在实测发现 G1 达不到目标时，才考虑 ZGC。

**实时交易/游戏服务（停顿要求 < 5ms）**：ZGC 或 Shenandoah。堆大（几十 G）时 ZGC 优势明显，因为它的停顿不随堆增长。

**批处理/离线计算（不在乎停顿）**：Parallel。吞吐最高，调优最简单。

**小内存容器（< 2G 堆）**：Serial 或者 G1 都行。ZGC 在小堆上收益不大，但它的额外内存开销（需要预留堆空间做并发整理）在小容器里可能反而有害。

**超大堆（> 100G）**：ZGC。G1 在这种规模下停顿很难压住，ZGC 的「停顿与堆大小无关」是决定性的优势。

## 一个常被忽略的成本：调优知识

ZGC 的参数很少（主要是 `ZAllocationSpikeTolerance`、`ZCollectionInterval`），看起来「不用调」。

但这也意味着：**出问题时你手里的旋钮很少。**

G1 有大量可调参数（区域大小、IHOP、混合收集比例），调优空间大，社区经验也多。对大多数团队，G1 的可控性反而更有价值。

## 怎么看实际表现

开启 GC 日志（JDK 9+ 统一日志）：

```bash
java -Xlog:gc*:file=gc.log:time,uptime,level,tags -XX:+UseG1GC ...
```

关键指标：

- **单次停顿的 P99 和最大值**——不是平均值。平均值会掩盖问题
- **Full GC 次数**——应该是 0。出现 Full GC 说明堆配置或对象存活率有问题
- **GC 时间占比**——超过 5% 就该关注
- **晋升失败（to-space exhausted）**——G1 的典型警告，说明回收速度跟不上分配

如果 Full GC 频繁，先别换收集器，先看是不是内存泄漏或者堆太小。换 GC 治不了内存泄漏。

## 一个实践结论

我在 2G 内存的服务器上跑过 G1 和 Serial，结论是：**在这个规模上，GC 选型不是瓶颈。**

瓶颈是内存总量本身——对象还没等到 GC，进程就被 OOM killer 杀了。

**GC 调优的收益，只有在「内存充足、GC 确实是瓶颈」时才成立。** 先确认这一点，再去纠结用哪个收集器。
