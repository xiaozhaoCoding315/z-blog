先说结论：**延迟双删有用，但它只能解决一个很具体的竞态，而且解决得并不彻底。**

如果把它当成万能药，你会在真正的一致性问题上浪费很多时间。

## 先看它想解决什么

标准流程是这样：

```
1. 删缓存
2. 更新数据库
3. sleep(几百毫秒)
4. 再删一次缓存
```

为什么需要第二次删除？因为存在这个竞态：

```
时刻   线程 A（更新）          线程 B（读）
t1     删缓存
t2                            缓存未命中，读数据库 → 旧值
t3     更新数据库（新值）
t4                            把旧值写回缓存
```

结果：数据库是新值，缓存是旧值，而且这个旧值会一直留着，直到过期。

第二次删除就是为了把 t4 写进去的脏数据再清掉。

## 它的前提是「读请求在写期间到达」

注意上面那个时序：**必须有并发读，而且读发生在新值写入数据库之前。**

如果这个时间窗里根本没有读请求，第二次删除就是白跑一趟。

反过来，如果读请求持续不断，问题也没这么简单——A 在 t4 删完之后，B 可能又写回一次旧值（如果 B 的读数据库操作发生在 t3 之前但写缓存发生在 t4 之后）。虽然概率极低，但**逻辑上不是零**。

<Callout type="warning" title="所以它不保证强一致">

延迟双删是「降低不一致窗口的概率」，不是「消除不一致」。真正需要强一致的地方（比如余额、库存），不该依赖这套方案。

强一致的方案只有两类：读时加锁（牺牲性能）、或者用数据库事务 + 版本号做校验（读出来发现版本不对就重试）。

</Callout>

## 「延迟多久」这个参数

这是最值得说的一点。网上大量文章说「延迟 500ms」，理由是「等读请求都结束」。

这个推理是错的。500ms 从哪来的？没有依据。正确的做法是：

**延迟时间 > 一次「读数据库 + 写缓存」的最长耗时。**

因为第二次删除必须发生在 B 完成写缓存之后。如果 B 的这次操作要 800ms（数据库慢查询、网络抖动），你删 500ms 之后，B 还是会写回旧值。

所以这个参数应该是：

```
delay > P99(读数据库耗时 + 写缓存耗时)
```

具体值要靠监控数据。如果没有监控数据，就说明这个问题你还没准备好解决——先加监控。

我在项目里的做法是取「该接口的 P99 延迟」的 1.5 倍，并且给一个上限（比如 2 秒），避免异常情况下 sleep 太久阻塞线程。

## 更好的做法：先更新数据库，再删缓存

这个顺序（Cache-Aside 的变体）其实比「先删缓存再更新」更常用：

```
1. 更新数据库
2. 删缓存
```

它只在一个更窄的窗口里出问题：

```
时刻   线程 A（更新）          线程 B（读）
t1                            缓存未命中，读数据库 → 旧值
t2     更新数据库（新值）
t3     删缓存
t4                            把旧值写回缓存
```

问题依然存在，但窗口更短（从「更新数据库的耗时」缩到「t1 到 t4」之间）。

而且它**不需要延迟**，实现简单，失败重试也容易做（删缓存失败就重试几次，或者丢进消息队列异步删）。

我的实际选择是：**先更新库再删缓存 + 缓存过期时间兜底**。缓存过期时间设得短一点（比如 5 分钟），把「万一不一致」的持续时间限制住。

## 什么时候需要更强的方案

三种情况我会考虑更复杂的方案：

**1. 数据变更频繁且读多。** 每次写都要删缓存，缓存命中率会掉。这时候考虑「写时更新缓存」而不是删，但要处理并发写的顺序问题（用版本号或者时间戳比较）。

**2. 多写者。** 多个服务都在写同一份数据，删缓存的时序更难保证。这时候需要分布式锁，或者把缓存更新收口到一个服务。

**3. 一致性要求高。** 前面说的余额、库存。这类数据我倾向于**根本不用缓存**，或者用「缓存只作为加速、读到后必须校验版本」的模式。

## 一个被忽略的细节：删除失败

`DEL` 失败怎么办？

如果删缓存失败而数据库已经更新，缓存就永久是旧值（直到过期）。所以删除操作必须可重试：

```java
public void evictAfterUpdate(String key, Runnable updateDb) {
    updateDb.run();
    try {
        redis.del(key);
    } catch (Exception e) {
        // 删除失败：进延迟队列重试，别让异常吞掉
        retryQueue.offer(key, delayMs(1000));
        log.warn("缓存删除失败，已加入重试队列: {}", key, e);
    }
}
```

更稳的做法是订阅数据库变更日志（binlog / CDC），由独立的消费者删缓存。这样即使业务代码里漏了删除，缓存也能被纠正。

## 小结

| 方案 | 一致性 | 复杂度 | 适用 |
| --- | --- | --- | --- |
| 先删缓存 + 延迟双删 | 弱（降低概率） | 中 | 读多写少，容忍短暂不一致 |
| 先更新库再删缓存 | 弱（窗口更短） | 低 | 大多数业务场景 |
| 版本号校验 | 强 | 高 | 关键数据 |
| 不用缓存 | 强 | 最低 | 一致性要求极高 |

延迟双删不是错，但它是个**补丁**，不是**方案**。先问清楚你的数据到底能容忍多久的不一致，再决定要不要上这套东西。
