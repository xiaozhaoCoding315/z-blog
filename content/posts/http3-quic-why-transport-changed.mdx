HTTP/2 当年最响亮的卖点是「多路复用」：一个 TCP 连接上并发跑几十个请求，不用再开六个连接排队。

但它有个没解决的问题：**多路复用发生在应用层，排队发生在传输层。**

## TCP 的队头阻塞没消失

HTTP/2 把多个请求的帧交错发到同一条 TCP 流上。如果其中一个帧在网络上丢了，TCP 不知道它是哪个请求的，只知道「这一段数据没到」。

于是 TCP 会等这个包重传成功，**在此期间整条连接上所有请求的数据都得等**。哪怕丢的那个包属于一个没人关心的图片请求，主文档也会卡住。

这就是 TCP 的队头阻塞（head-of-line blocking）。HTTP/2 把应用层的队头阻塞解决了，却把问题原样推给了 TCP。

<Callout type="info" title="为什么不能改 TCP">

TCP 已经部署了四十多年。要改它的重传语义，得动操作系统内核、动所有中间设备（路由器、防火墙、NAT）。这个改动量在现实中不可能完成。

所以 QUIC 的选择是：**在 UDP 之上重新实现一套可靠的传输层**，把控制权拿回用户态。

</Callout>

## QUIC 做了什么

QUIC 运行在 UDP 上，自己实现可靠性、拥塞控制、多路复用。关键差异在于：

| 能力 | TCP + TLS | QUIC |
| --- | --- | --- |
| 多路复用 | 应用层（HTTP/2） | 传输层原生 |
| 丢包影响范围 | 整条连接 | 单个流 |
| 握手 | TCP 三次 + TLS 握手 | 合并为一次（TLS 1.3 内建） |
| 连接迁移 | 换 IP 就断 | 用连接 ID 保持 |
| 加密 | 可选（TLS 在外层） | 强制，传输头也加密 |

**每个流独立。** 一个流丢包只影响这个流，其他流照常前进。这是 HTTP/3 真正的收益，不是「更快」，是「卡的时候只卡一个」。

**握手更快。** QUIC 把传输握手和 TLS 1.3 握手合并，首次连接一个往返，重连可以用 0-RTT（用之前的会话票据直接发数据）。

**连接迁移。** 手机从 Wi-Fi 切到 4G，IP 变了，TCP 连接必然断。QUIC 用连接 ID 而不是四元组标识连接，切换网络后连接可以继续。这对移动端是实打实的体验差别。

## 中间设备的麻烦

QUIC 走 UDP。很多企业网络、老防火墙对 UDP 的处理很粗暴：限速、直接丢弃、或者只放行 53 端口（DNS）。

这就是为什么浏览器在 HTTP/3 上通常采用「Happy Eyeballs」式的策略：同时尝试 QUIC 和 TCP，哪个先成功用哪个，并且记住结果。如果 QUIC 一直失败，就回退到 HTTP/2，不会让用户干等。

对服务端来说，部署 HTTP/3 通常意味着：

- 在 443 端口同时监听 TCP（HTTP/2）和 UDP（HTTP/3）
- 在响应头里加 `Alt-Svc: h3=":443"`，告诉客户端「你也可以用 HTTP/3」
- CDN 层开启（大多数 CDN 早就支持了）

单机自建的场景下，收益往往不明显——因为延迟的大头是「用户到机房的距离」，而不是协议本身。QUIC 的价值主要在**弱网、移动端、跨运营商**这些场景。

## 它没有解决的事

HTTP/3 不是银弹：

**CPU 成本更高。** 加密在用户态做，没有 TCP 那种内核优化和硬件卸载。高吞吐场景下 CPU 占用会比 HTTP/2 高。

**调试更难。** 抓包工具对 UDP + 加密传输头的支持不如 TCP 成熟。出问题时排查链路更长。

**首字节延迟不一定更短。** 0-RTT 只在重连时有效，首次访问还是得走完整握手。

**队头阻塞没有消失，只是换了位置。** 单条 QUIC 流内部依然有序，一个流里丢包照样要等。区别是影响范围从「整条连接」缩小到「这一个流」。

## 要不要上

我的判断标准：

- **面向公网、用户分布广、移动端占比高** → 值得，通常 CDN 层就能开，成本低
- **内网服务、单机房、用户就近** → 收益有限，先优化数据库和接口
- **高吞吐的数据传输** → 谨慎，CPU 成本和调试成本要算进去

协议演进的方向是明确的：**把控制权从内核拿到用户态，把「连接」和「网络地址」解耦。** HTTP/3 是这个方向上的第一步，不是终点。
