「用 JWT 就不用存 session 了，服务端无状态。」

这句话在技术文章里出现得太频繁，以至于很多人以为 JWT 的核心优势是「无状态」。它确实是，但这正是它最大的问题来源。

## JWT 里到底有什么

一个 JWT 是三段 base64url：

```
header.payload.signature
```

`payload` 是明文可读的 JSON（只是 base64 编码，不是加密）。`signature` 是服务端用私钥对前两段的签名。

所以：

- **任何人**都能读到 payload 内容
- **只有服务端**能验证内容没被篡改

把用户 ID、角色、过期时间放进 payload，服务端验签后直接信任——不需要查数据库。这就是「无状态」。

## 无状态的代价

无状态的反面是「失去控制」。

签发一个 7 天有效期的 token 之后，如果用户改了密码、被管理员封号、或者 token 泄露了，**你没法让它立刻失效**。服务端验签通过，它就有效。

常见的补救方案，以及它们的真实代价：

**缩短有效期（比如 15 分钟）+ refresh token。** 这是最主流的做法，但它没解决问题，只是把问题转移了——refresh token 本身存哪？如果存数据库，那你还是要有状态。如果也是 JWT，那它同样不能撤销，只是窗口变长了。

**维护黑名单。** 每个请求查一次「这个 token 是否被吊销」。这等于放弃了无状态，而且每次请求多一次存储查询。

**用版本号。** 用户信息里存一个 `token_version`，JWT 里带上签发时的版本号，验证时比对。改密码就递增版本号，旧 token 全部失效。这需要每次请求读一次用户信息（可以缓存），本质还是有状态，只是状态很小。

<Callout type="warning" title="别把 JWT 当加密用">

payload 是明文。有人会把手机号、邮箱甚至角色权限塞进去，以为「签名了就安全」。

签名保证的是**完整性**（没被改），不是**机密性**（没被读）。任何拿到 token 的人都能解出 payload。敏感信息不要放进去。

</Callout>

## 该不该用 JWT

我的判断标准不是「要不要无状态」，而是**「谁在验证身份」**。

**用 JWT 的场景：**

- 跨服务调用。A 服务签发，B、C 服务验签，不用共享 session 存储
- 短时有效的凭证。比如文件下载链接、密码重置链接、一次性邀请
- 第三方集成。OAuth 的 access token 天然是这种形态

**不该用 JWT 的场景：**

- 单一后端的网站会话。一个 Redis 就够了，而且能随时踢人
- 需要精细权限撤销的场景
- 你需要「立刻让某人下线」的时候

对个人博客这种单服务场景，我倾向用**服务端 session**。理由是：一个 Redis key 的存储成本可以忽略，而「能随时撤销」的价值很高。

## 一个常见的错误：把用户信息全塞进去

```json
{
  "sub": "user_42",
  "name": "张三",
  "email": "z@example.com",
  "roles": ["admin", "editor"],
  "avatar": "https://...",
  "permissions": [...]
}
```

问题在于：**这些信息在 token 有效期内是冻结的。**

用户改了昵称，前端还显示旧的。管理员撤了某个角色，用户照样有权限，直到 token 过期。

正确做法是只放**标识**，不放**属性**：

```json
{
  "sub": "user_42",
  "ver": 3,
  "iat": 1758000000,
  "exp": 1758000900
}
```

属性在服务端查（可以缓存几十秒）。这样角色变更能在秒级生效，而不是等 token 过期。

## 几个实现细节

**`alg: none` 攻击。** 如果验证代码信任 header 里的 `alg` 字段，攻击者可以把 `alg` 改成 `none` 并去掉签名，某些库会直接放行。必须**在代码里硬编码允许的算法**，不要读 header 决定。

**密钥强度。** HS256 用同一个密钥签名和验证，密钥泄露等于全部伪造。至少 256 位随机。RS256/ES256 用非对称密钥，验证方只拿到公钥，泄露风险更小。

**`exp` 必须校验。** 而且要考虑时钟漂移，通常允许几十秒的偏差。

**不要在 URL 里传 token。** URL 会进日志、进 Referer、进浏览器历史。放 `Authorization` 头里。

## 小结

JWT 是一个**签名的、自包含的、不可撤销的**凭证。

前两个特性是优点，第三个是硬约束。如果你需要撤销能力（几乎所有面向用户的系统都需要），就必须额外维护状态——那么「无状态」这个卖点就不成立了。

所以问题不是「用不用 JWT」，而是：**你的系统需要多快地撤销一个身份？** 答案决定你该用 session 还是 JWT，以及 JWT 的有效期该设多长。
