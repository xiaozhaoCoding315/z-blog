同一个意思，用中文写和用英文写，token 数可能差两倍。

这直接决定了：上下文窗口能装多少内容、一次调用花多少钱、为什么「看起来不长的对话」会超限。

## Token 是什么

模型不直接处理字符。输入文本先被切成 token，每个 token 对应词表里的一个 ID。

词表大小通常是几万到十几万。切分规则由 BPE（Byte Pair Encoding）之类的算法训练出来：**高频的字符串组合合并成一个 token，低频的拆成更小的片段。**

所以 token 的长度不固定：

- `"the"` 是一个 token
- `"unbelievable"` 可能是 `un` + `believ` + `able` 三个
- 一个中文字符经常是 1 到 2 个 token

## 为什么中文更费

关键在于：**主流词表是在以英文为主的语料上训练的。**

英文有天然的空格分隔，高频词（`the`、`and`、`of`）都是单个 token。常见的英文单词平均约 1 token / 4 个字符。

中文没有空格，而且词表里中文的子词单元覆盖不如英文充分。结果：

| 文本 | 字符数 | 大致 token 数 | 比例 |
| --- | --- | --- | --- |
| 英文 | 100 | ~25 | 0.25 |
| 中文 | 100 | ~100–150 | 1.0–1.5 |

也就是说，**同样的信息量，中文的 token 消耗可能是英文的 2 到 4 倍**。

这不是精确结论——不同模型的中文词表覆盖差别很大，有的模型专门扩了中文词表，比例会好一些。但「中文比英文费 token」这个方向是确定的。

<Callout type="info" title="别用字符数估 token">

「我这篇文章 3000 字，应该没超上下文」——这个推理是错的。

3000 个中文字符可能是 3000 到 4500 个 token。加上系统提示、历史对话、输出预留，很容易就超了。

要估就实测：用对应模型的 tokenizer 跑一遍。

</Callout>

## 实测比估算可靠

各家都提供了计数接口或库：

```ts
// Anthropic
const { input_tokens } = await client.messages.countTokens({
  model,
  messages,
  system,
});
```

```python
# OpenAI
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4o")
print(len(enc.encode("这是一段中文测试")))
```

注意：**不同模型的 tokenizer 不一样**，用 A 模型的 tokenizer 估 B 模型的数量会偏。同一家的不同代模型也可能换词表。

## 实际影响

**1. 上下文窗口的有效容量**

标称 200K 的窗口，如果内容是中文，实际能装的信息量可能只有英文的一半。设计长文档处理流程时，要按实际 token 数规划分块。

**2. 成本**

输入输出都按 token 计费。中文内容多的应用，同样的「页数」成本更高。

**3. 分块策略**

RAG 的分块如果按字符数切（比如每块 500 字），实际 token 数波动很大。中文块可能 500 token，英文块可能 150 token。应该按 token 数切，或者按字符切之后再按 token 二次校验。

**4. 输出截断**

`maxOutputTokens` 是 token 数。设 800，中文大概能写 500 到 700 字。设太小会导致回答中途被切断。

## 一些省钱但不太影响质量的技巧

**精简系统提示。** 系统提示每次都进上下文，是最该优化的部分。把「你是一个专业的、乐于助人的、经验丰富的……」这类废话删掉，省下来的是每次调用的固定成本。

**用英文写指令，用中文输出。** 指令部分用英文更省 token，且模型的指令遵循能力在英文上通常更稳。输出语言由内容决定。

**不要在每轮都重发完整历史。** 多轮对话的成本是累积的——第 10 轮的输入包含了前 9 轮。用 prompt caching 可以大幅降低重复部分的成本（缓存命中的部分通常只收很低的费用）。

**输出格式要短。** 让模型返回 JSON 比返回「好的，结果如下：……希望有帮助！」要省得多。这也是结构化输出的另一个好处。

## 一个常见误解

「token 数约等于单词数」——对英文大致成立（一个单词可能 1 到 2 个 token），但对中文完全不成立，对代码也不成立（代码里的符号、缩进都会消耗 token，而且常常一个符号一个 token）。

代码的 token 密度往往比自然语言更高。一个 200 行的 Python 文件可能 2000+ token。把整个代码库塞进上下文之前，先算一遍。

**估不准就测。** 这是唯一可靠的结论。
