做一个复杂任务时，第一个念头往往是「拆成多个 Agent，各自负责一块，再汇总」。

这个思路在很多场景下是错的。多 Agent 的协调成本（上下文传递、状态同步、错误传播、调试难度）经常超过它带来的收益。

这篇梳理三种编排形态，以及各自适用什么。

## 形态一：单 Agent + 工具

一个循环：

```
while not done:
    response = model(messages, tools)
    if no tool_calls: break
    for call in response.tool_calls:
        messages.append(execute(call))
```

这就是最基础的 Agent。它能处理的任务范围比很多人想象的要广——只要工具设计得好。

**优势：**

- 上下文是连续的，模型能看到所有中间结果
- 调试简单：一条消息序列，从头看到尾
- 没有「A 不知道 B 做了什么」的问题
- 成本可控：一次任务只有一条对话链

**适用：** 大部分单领域任务。查资料写报告、修一个 bug、整理数据、回答需要多次检索的问题。

我见过的过度设计里，最常见的形态是：一个本来可以用「单 Agent + 三个工具」解决的任务，被拆成了四个 Agent，然后花两周时间调它们之间的消息格式。

## 形态二：工作流（固定编排）

不是让模型决定流程，而是**你决定流程**，模型只负责每个节点内的判断。

```python
def pipeline(query):
    plan = planner_agent(query)          # 拆解任务
    results = []
    for step in plan.steps:
        results.append(executor_agent(step))   # 执行
    report = writer_agent(query, results)      # 汇总
    return report
```

**优势：**

- 流程可控，可预测
- 每个节点的输入输出可以单独测试
- 出错时知道是哪个阶段
- 可以做并行（如果步骤之间独立）

**劣势：**

- 流程是写死的，遇到流程外的情况就崩
- 每个节点之间的信息传递需要你手动设计（什么该传，什么不该传）

**适用：** 流程稳定、步骤明确的场景。文档处理流水线、代码审查（检查项固定）、批量数据加工。

判断标准：**如果这个流程你画得出来一张确定的图，就用工作流。** 如果画不出来（因为下一步取决于上一步的结果，且可能性太多），才考虑交给 Agent 自己决策。

## 形态三：多 Agent 协作

多个 Agent 有各自的上下文，通过某种协议通信（消息传递、共享黑板、或者一个「主管」Agent 调度）。

**优势：**

- 可以并行，适合「四个独立的信息源」这类任务
- 每个 Agent 的上下文更聚焦（不用装下所有东西）
- 可以做「对抗」结构：一个生成，一个审查

**劣势（也是大多数失败的原因）：**

- **上下文分裂。** A 知道的信息，B 不知道。你需要在 Agent 之间传递摘要，而摘要一定会丢信息。
- **错误放大。** 一个 Agent 的错误会沿着链路传播，而且下游 Agent 没有能力识别「上游给的是错的」。
- **调试困难。** 多个对话序列交错，出问题时很难定位。
- **成本。** 每个 Agent 都有自己的系统提示和上下文，总 token 消耗远高于单 Agent。

**适用：** 任务确实可以自然分解，且各部分之间**耦合很弱**。典型例子：

- 并行采集（同时查四个数据源，各自独立）
- 生成 + 评审（评审者只看结果，不看生成过程）
- 不同视角的分析（法律视角、财务视角、技术视角）

判断标准：**子任务之间需不需要频繁交换中间状态？** 需要 → 别拆；不需要 → 可以拆。

## 一个实际的分层建议

我现在的做法是**混合**，而不是纯用某一种：

```
主管（工作流，写死）
  ├── 并行检索 Agent × 3   ← 多 Agent，因为独立
  └── 汇总 Agent           ← 单 Agent，需要看全部结果
```

外层用工作流保证可控，内层在「确实独立」的地方用多 Agent 并行。

关键是：**并行的那几个 Agent 之间不通信。** 它们各自完成，结果交给汇总者。一旦它们需要互相对话，协调成本就会爆炸。

<Callout type="warning" title="别用多 Agent 做「分工」">

「一个 Agent 写前端，一个写后端，一个写测试」——这个拆分看起来合理，实际很糟。

三个 Agent 要共享接口定义、数据结构、命名约定。任何一处不一致，代码就合不起来。而这些信息在单 Agent 里是天然共享的。

**共享上下文越多，越不该拆。**

</Callout>

## 成本对比

粗略的量级（同一任务）：

| 形态 | token 消耗 | 调试难度 | 可控性 |
| --- | --- | --- | --- |
| 单 Agent | 1× | 低 | 中（模型自己决定） |
| 工作流 | 1.2× | 低 | 高（流程写死） |
| 多 Agent | 2–4× | 高 | 低 |

多 Agent 的成本来自：每个 Agent 的系统提示、重复的上下文、以及 Agent 之间的消息传递。

## 我的选择顺序

1. **能用工作流就用工作流。** 流程写死，模型只在节点内做判断。可控、可测、便宜。
2. **流程不确定时，用单 Agent + 好工具。** 让模型自己决定顺序，但工具要设计得清晰。
3. **只有「任务天然可并行且互相独立」时才用多 Agent。**
4. **永远不要为了「看起来架构先进」而拆。**

最后一条最重要。多 Agent 是一种**解决特定问题的手段**（上下文分裂、并行、对抗审查），不是**架构升级的方向**。用错了地方，它只会让系统更难理解、更难调试、更贵。
