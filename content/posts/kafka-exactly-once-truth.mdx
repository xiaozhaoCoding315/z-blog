消息队列的投递语义有三档：

- **至多一次（at-most-once）**：可能丢，不会重
- **至少一次（at-least-once）**：不会丢，可能重
- **精确一次（exactly-once）**：不丢不重

大部分系统承诺「至少一次」，因为它实现简单：发出去，等确认，没确认就重发。代价是重复。

Kafka 从 0.11 版本开始宣称支持 exactly-once。这个说法值得拆开看。

## 它靠什么做到

两个机制：

**1. 幂等生产者。** 每条消息带一个序列号，broker 按「生产者 ID + 分区 + 序列号」去重。同一个生产者重发的消息会被识别并丢弃。

这解决了「生产端重试导致的重复」。

**2. 事务。** 生产者可以把「发多条消息 + 提交消费位点」打包成一个事务，原子提交。要么全部生效，要么全部不生效。

这解决了「消费-处理-再发送」这条链路上的重复。

```java
producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(record1);
    producer.send(record2);
    producer.sendOffsetsToTransaction(offsets, consumerGroup);
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
}
```

## 边界在哪

关键在最后那一行：**`sendOffsetsToTransaction` 提交的只是 Kafka 的位点。**

事务保证的是：
- 我发出的消息，要么全到，要么全不到
- 我的消费位点，和这些消息一起提交

**它不保证：你处理消息时写的数据库，和这些消息在同一个事务里。**

所以这条链路：

```
Kafka → 消费者 → 写 PostgreSQL → 提交
```

如果消费者写完 PostgreSQL 之后崩了，位点没提交，重启后这条消息会被重新消费，数据库里就多了一条重复记录。

Kafka 的事务管不到你的 PostgreSQL。

## 那到底怎么做到端到端精确一次

只有两条路：

**路一：让副作用本身幂等。**

这是最实用的做法。给每条消息一个业务幂等键（比如订单号），写入时用唯一约束：

```sql
INSERT INTO orders (order_id, amount, status)
VALUES ($1, $2, 'created')
ON CONFLICT (order_id) DO NOTHING;
```

重复消费时，第二次插入被唯一约束挡掉，结果等价于「只处理了一次」。

这个方案要求：**你的业务能定义幂等键。** 大多数写操作可以（创建订单、扣款用流水号），少数不行（比如「余额加 10」这种增量操作——那就要改成「设置余额为 X」或者用流水表）。

**路二：把位点提交纳入同一个事务。**

如果消费的副作用写在支持事务的存储里，可以让「位点」和「业务数据」写进同一个数据库事务：

```
BEGIN;
  INSERT INTO orders ...;
  UPDATE consumer_offsets SET offset = $1 WHERE partition = $2;
COMMIT;
```

这样两者原子提交，要么都成功要么都回滚。代价是你要自己管理位点，不能用 Kafka 的自动提交。

这个模式在流处理框架里很常见（Flink 的 checkpoint、Spark Structured Streaming 的 offset 管理都是这个思路）。

<Callout type="warning" title="外部 API 无法参与事务">

如果副作用是调用第三方 API（发短信、发邮件、调支付），你**没有任何办法**把它纳入事务。

这种情况下唯一的选择是幂等：给请求带一个幂等键，让对方的接口自己保证重复调用不重复执行。如果对方不支持，那就只能接受「至少一次」，并在业务层做去重（比如发送前查记录）。

</Callout>

## 一个容易忽略的地方：消费者组的位点

`enable.auto.commit = true`（默认）意味着位点按时间间隔自动提交。这意味着：

```
处理消息 A（失败）
自动提交触发，位点推进到 A 之后
```

这条消息就永久丢了。

用事务或幂等处理时，必须关掉自动提交，手动控制位点。

## 实际怎么选

我的判断顺序：

1. **副作用能定义幂等键吗？** 能 → 用幂等，简单可靠，不依赖 Kafka 事务
2. **副作用是写同一个数据库吗？** 是 → 可以用「位点 + 业务数据同事务」
3. **副作用是外部 API 吗？** → 幂等键交给对方，对方不支持就只能接受至少一次
4. **以上都不行** → 重新设计，别指望消息队列

## 为什么 Kafka 的说法容易误导

因为「exactly-once」这个词在 Kafka 的语境里是**限定于 Kafka 内部**的。它的准确表述是：

> Kafka 保证「消息在 Kafka 内部的传输」和「消费位点的提交」是原子的。

这确实很有价值——它消除了「消息发出去了但位点没提交」这类 Kafka 自身的重复。但它不能延伸到 Kafka 之外。

流处理框架里说 exactly-once，通常也是这个意思：**在框架管理的状态和 source/sink 之间**。一旦 sink 是外部系统，语义就退化了。

理解这个边界，比记住「Kafka 支持 exactly-once」这个结论有用得多。
