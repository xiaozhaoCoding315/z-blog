多轮对话的成本是累积的：第 10 轮的输入包含前 9 轮的全部内容。如果系统提示还有 2000 token，那么第 10 轮的输入可能是 20000 token。

Prompt caching 就是为这件事设计的：**把不变的前缀缓存起来，后续请求只按增量计费。**

## 规则很简单，也很严格

缓存按**前缀**匹配。从第一个 token 开始，逐 token 比对，直到出现差异为止。差异点之前的部分命中缓存，之后的部分全价。

所以顺序极其重要：

```
[系统提示] [工具定义] [历史对话] [当前问题]
     ↑ 这部分不变，可以缓存
```

如果系统提示里有时间戳：

```
你是助手。当前时间：2026-11-01 14:32:07
```

那每次请求的前缀都不一样，**永远不命中**。

同理，如果工具定义数组的顺序不固定（比如从 Map 遍历出来），前缀也会变。

## 正确的排列方式

把「变化最少」的放最前面：

1. **系统提示**（几乎不变）
2. **工具定义**（很少变）
3. **参考资料 / 长文档**（会话期间不变）
4. **对话历史**（逐轮增长）
5. **当前问题**（每次都变）

这样每一轮都能命中前四段的大部分。

<Callout type="tip" title="动态内容一律后置">

任何「每次都可能不同」的内容，都要放到最末尾。

常见错误：把当前时间、用户 IP、请求 ID 塞进系统提示。这些看起来「应该在第一段」，实际是缓存杀手。

正确做法：放到最后一条 user 消息里，或者干脆通过工具调用的结果提供。

</Callout>

## 缓存的最小长度

不是所有内容都值得缓存。太短的前缀（比如几百 token）可能低于最小缓存长度，或者收益不够覆盖写缓存的成本。

写缓存通常比读缓存贵（有的实现是 1.25 倍输入价格），读缓存便宜很多（0.1 倍左右）。

所以经济账是：

```
缓存写入成本 = 前缀长度 × 1.25 × 单价
每次命中节省 = 前缀长度 × 0.9 × 单价
盈亏平衡点 = 1.4 次左右
```

也就是说，**同一个前缀只要复用两次以上，就划算。**

对多轮对话、批量处理同一份文档的场景，这个条件几乎总是成立。

## 缓存的有效期

缓存不是永久的。通常有几分钟到一小时的 TTL（不同实现不同），每次命中会刷新 TTL。

这意味着：

- 高频对话场景，缓存一直有效
- 一天只调几次的场景，缓存基本用不上

如果业务是「每天凌晨批量处理一批文档」，那 prompt caching 帮助有限——缓存早就过期了。

## 一个容易忽略的收益：延迟

省钱是显性的，延迟是隐性的但同样重要。

缓存命中的部分不需要重新处理，**首 token 延迟（TTFT）会明显降低**。对交互式应用，这直接决定用户觉得「快不快」。

我实测过一个场景：20000 token 的输入，命中缓存后 TTFT 从 2 秒降到 0.5 秒左右。体感差别很大。

## 怎么验证有没有命中

响应里通常有字段告诉你缓存用了多少：

```json
{
  "usage": {
    "input_tokens": 200,
    "cache_read_input_tokens": 18000,
    "cache_creation_input_tokens": 0
  }
}
```

`cache_read_input_tokens` 大于 0 才说明命中。

如果一直是 0，按这个顺序排查：

1. 前缀里有没有时间戳、随机 ID、UUID
2. 工具定义的顺序是否稳定（JSON 序列化要保持键顺序）
3. 内容是不是真的完全一致（多余的空格、换行也会导致不匹配）
4. 请求间隔是不是超过了 TTL

第 3 条最隐蔽。我遇到过一次：系统提示是从模板字符串拼出来的，其中一个变量是 `undefined`，导致有时输出 `undefined` 有时输出空字符串。前缀就在两种形态间来回跳，缓存命中率只有 50%。

## 不适合缓存的场景

**每次输入都不同。** 比如「用户上传一份文档，问一个问题」——文档每次都变，缓存没意义。

**短输入。** 几百 token 的请求，缓存收益小于复杂度成本。

**一次性的批处理。** 缓存还没来得及复用就过期了。

## 一个结构化的建议

如果你的应用有「固定的系统提示 + 可变的用户输入」，现在就该上缓存。做法是：

1. 把系统提示和工具定义抽成常量，确保每次序列化结果完全一致
2. 把所有动态内容（时间、用户信息、请求上下文）放到消息列表末尾
3. 在系统提示末尾加一个明确的缓存标记（如果 API 需要显式声明）
4. 监控 `cache_read_input_tokens`，把它当成一个核心指标

**这一步的投入产出比，比大部分 prompt 优化都高。** 因为它省的是真金白银和真实的等待时间。
