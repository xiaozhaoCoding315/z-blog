限流的实现看起来很简单：数个数，超了就拒。

但「怎么数」这件事，四种经典算法给出的答案差别很大。选错了，要么限不住，要么把正常用户也限了。

## 一、固定窗口

最直觉的做法：把时间切成固定长度（比如 1 分钟），每个窗口一个计数器。

```python
def allow(user_id):
    key = f"rate:{user_id}:{now // 60}"
    count = redis.incr(key)
    if count == 1:
        redis.expire(key, 60)
    return count <= 100
```

简单，一次 `INCR` 搞定，内存占用极小。

**问题是边界。**

```
第 1 分钟最后 1 秒：放行 100 个
第 2 分钟最初 1 秒：放行 100 个
```

跨过窗口边界的两秒内，实际放行了 200 个。如果下游只能承受 100/分钟，这里就会被打穿。

这不是理论问题。攻击者或者一个失控的客户端，只要踩准边界重试，就能拿到两倍配额。

## 二、滑动窗口日志

记录每次请求的时间戳，检查「最近 60 秒内有多少条」。

```python
def allow(user_id):
    key = f"rate:{user_id}"
    now_ms = time.time() * 1000
    pipe = redis.pipeline()
    pipe.zremrangebyscore(key, 0, now_ms - 60000)   # 清理过期
    pipe.zcard(key)                                  # 计数
    pipe.zadd(key, {str(now_ms): now_ms})
    pipe.expire(key, 60)
    _, count, _, _ = pipe.execute()
    return count < 100
```

精确。任何 60 秒的窗口内都不会超过 100 个。

**代价是内存。** 每个用户要存最多 100 个时间戳。十万活跃用户就是千万级的有序集合条目，Redis 内存会很难看。

另一个问题是**没有平滑性**：如果客户端在 1 秒内打满 100 个，剩下 59 秒全被拒。这对用户体验是灾难——它不允许任何突发。

## 三、滑动窗口计数（折中）

把窗口切成小格（比如 60 个 1 秒的格子），用「上一格的加权值 + 当前格的实际值」估算：

```
estimated = prev_count * (1 - elapsed_ratio) + curr_count
```

内存从「每个请求一个条目」降到「每格一个计数」，精度也够用。这是很多生产系统的实际选择。

它仍然不是精确的，但误差被限制在「一格」的量级，而且**允许短时间突发**——因为只要估算值没超，请求就放行。

## 四、令牌桶

核心思想：桶里放令牌，按固定速率补充，请求来了取一个。桶满则不再补充（限制突发上限），桶空则拒绝。

```
capacity = 100      # 桶容量 = 允许的最大突发
rate = 10           # 每秒补充 10 个
```

它同时约束了两个维度：

- **长期速率** 受 `rate` 限制
- **瞬时突发** 受 `capacity` 限制

这正好对应大多数真实需求：平均每分钟 100 次，但允许偶尔连发 20 个。

实现上不需要定时器，用「惰性补充」就够了：

```python
def allow(key, capacity=100, rate=10):
    now = time.time()
    data = redis.hgetall(key)          # {tokens, last_ts}
    tokens = float(data.get("tokens", capacity))
    last = float(data.get("last_ts", now))

    # 距上次请求过去了多久，补多少令牌
    tokens = min(capacity, tokens + (now - last) * rate)

    if tokens < 1:
        redis.hset(key, mapping={"tokens": tokens, "last_ts": now})
        return False

    tokens -= 1
    redis.hset(key, mapping={"tokens": tokens, "last_ts": now})
    return True
```

**注意**：这段代码在并发下不是原子的（读-改-写有竞态）。生产里要么用 Lua 脚本，要么用 Redis 的 `WATCH`/事务，或者干脆接受轻微误差。

<Callout type="warning" title="令牌桶的常见误用">

把 `capacity` 设得等于 `rate`，令牌桶就退化成「匀速放行」，失去了抗突发的意义。

`capacity` 应该按「后端能承受的瞬时并发」来定，通常比 `rate` 大几倍。

</Callout>

## 五、漏桶

请求进队，以固定速率流出。队列满则拒绝。

区别在于：**令牌桶允许突发，漏桶强制匀速。**

如果下游是「每分钟只能处理 100 个，多一个就排队」的批处理系统，漏桶更合适——它保证输出速率恒定。代价是延迟：请求要在队列里等。

## 怎么选

| 算法 | 精度 | 内存 | 抗突发 | 适用 |
| --- | --- | --- | --- | --- |
| 固定窗口 | 差（边界双倍） | 极低 | 否 | 粗粒度保护，容忍误差 |
| 滑动窗口日志 | 精确 | 高 | 否 | 低频接口、强一致限流 |
| 滑动窗口计数 | 近似 | 中 | 部分 | 通用场景 |
| 令牌桶 | 精确（速率层面） | 低 | 是 | 对外 API、需要突发的场景 |
| 漏桶 | 精确 | 中 | 否（削峰） | 保护下游批处理 |

我的默认选择是**令牌桶**。原因很实际：真实流量从来不均匀，用户的点击是成簇的。用滑动窗口日志那种「不允许突发」的限流，会把一波正常操作打成 429，然后用户重试，形成更糟的流量模式。

## 几个容易忽略的细节

**分布式限流的一致性。** 多实例部署时，每个实例各限一份，总限额就变成 N 倍。要么用 Redis 做集中计数，要么按实例数把本地限额除下去（后者有误差，但省一次网络往返）。

**限流键的选择。** 按 IP 限流会误伤 NAT 后面的整个公司；按用户 ID 限流，未登录用户没有 ID；按 API key 限流，key 泄露后攻击者拿到全额配额。通常是多级：先按 IP 粗限，再按用户细限。

**被限之后要告诉客户端等多久。** 返回 `429` 时带上 `Retry-After`，否则客户端只能盲目重试，反而加剧拥塞。

**限流要能观测。** 统计「被拒率」。如果某个接口被拒率突然从 0.1% 涨到 5%，要么是有人在刷，要么是你的阈值设错了——两种情况都得看。
