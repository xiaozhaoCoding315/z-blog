「加了索引为什么还是慢？」

这个问题我在项目里遇到过很多次。教科书答案通常是「没满足最左前缀原则」，但真实情况往往更绕。下面六个场景都是我实际排查过的，每个都附上 `EXPLAIN` 的判断依据。

## 一、隐式类型转换

字段是 `VARCHAR`，查询传了个数字：

```sql
-- user_id 是 varchar(32)
SELECT * FROM orders WHERE user_id = 12345;
```

MySQL 会把字符串列转成数字再比较，这个转换发生在**每一行**上，索引直接失效。`EXPLAIN` 里 `type` 会从 `ref` 掉到 `ALL`。

反过来的情况更隐蔽：字段是 `INT`，传了字符串 `'123'`。这个通常**不会**失效，因为字符串会被转成数字，索引还能用。

<Callout type="warning" title="判断方法">

看 `EXPLAIN` 的 `key` 列为 `NULL`，同时 `rows` 接近表的总行数，基本就是这类问题。另一种确认方式是把查询参数的类型和字段类型对一遍——尤其是从 JSON 反序列化来的参数，数字很容易变成字符串，或者反过来。

</Callout>

## 二、函数包在索引列上

```sql
-- 失效
SELECT * FROM users WHERE DATE(created_at) = '2026-08-01';

-- 有效
SELECT * FROM users
WHERE created_at >= '2026-08-01 00:00:00'
  AND created_at <  '2026-08-02 00:00:00';
```

第一条对索引列做了运算，索引里存的是原始值，没法直接用来定位。第二条是范围查询，索引可以用。

这个坑最常见的来源是「按天统计」的需求。写的时候顺手一个 `DATE()`，性能就没了。改成左闭右开的时间区间，语义一样，索引可用。

从 MySQL 8.0.13 开始可以用函数索引（`CREATE INDEX ... ((DATE(created_at)))`），但那是另一种思路：让索引去适配查询，代价是多一份索引的写入成本。范围写法通常更划算。

## 三、OR 连接的两边不是都有索引

```sql
SELECT * FROM articles
WHERE author_id = 42 OR category_id = 7;
```

如果 `author_id` 有索引而 `category_id` 没有，优化器很可能干脆两个都不用，走全表扫描。

原因是 OR 的语义要求两边都能快速定位。只要有一边退化成全扫，整体就必须全扫，那还不如一开始就全扫。

解法有两个：给两边都建索引（MySQL 会做 index merge，但不保证每次都选），或者拆成两个查询再合并结果。后者更可控。

## 四、LIKE 以通配符开头

```sql
SELECT * FROM posts WHERE title LIKE '%索引%';   -- 失效
SELECT * FROM posts WHERE title LIKE '索引%';    -- 有效
```

前缀通配符让 B+ 树无法定位起点。这个大家都知道，但真正的问题是——**需求方经常就是要模糊搜中间**。

如果确实要这种搜索，别硬怼 B+ 树：全文索引（`FULLTEXT`）、倒排索引方案、或者把搜索挪到专门的搜索引擎。指望在 MySQL 上做任意位置的子串匹配，怎么调都调不好。

## 五、统计信息过期

这一类最折磨人，因为它**不会立刻出错，而是过一阵子突然出错**。

我遇到过一次：同一个查询，上线时走索引 3ms，两周后变成 400ms。代码没改，数据量从 10 万涨到 300 万。

原因是优化器按统计信息估算成本。数据分布变了，但统计信息没及时更新，它还是按老数据判断「走索引不划算」。

排查方式：

```sql
SELECT * FROM mysql.innodb_table_stats WHERE table_name = 'orders';
SHOW INDEX FROM orders;
```

更新：

```sql
ANALYZE TABLE orders;
```

生产环境一般有定时任务在跑，但如果你的表写入很频繁、或者数据分布有明显倾斜（比如 90% 的行都是同一个 `status`），统计信息很容易失真。

<Callout type="tip" title="更稳的办法">

对那种「绝大多数行值相同」的字段，索引本来就不该建——优化器判断出「查这个值要扫 90% 的表」，自然会放弃索引。这时候正确的做法是改查询条件（加上更严格的过滤），而不是强行 `FORCE INDEX`。

</Callout>

## 六、最左前缀被自己绕过去了

```sql
-- 索引是 (status, created_at)
SELECT * FROM orders WHERE created_at > '2026-08-01';   -- 只能用后一段？不，用不了
```

跳过了最左列，索引整体不可用。这个是最经典的，但真实场景里它常常以变体出现：

```sql
-- 看起来用了，其实只用到了 status
SELECT * FROM orders
WHERE status IN ('paid', 'shipped') AND created_at > '2026-08-01';
```

`IN` 会让范围条件分裂成多段，`created_at` 那一段能不能用取决于优化器怎么展开。多数情况下它只能用到 `status`，后面的 `created_at` 退化成过滤而不是定位。

这类问题的判断办法是看 `EXPLAIN` 的 `key_len`——它告诉你实际用了索引的多少个字节。如果只用了第一列的长度，说明后面的没生效。

## 一个通用的排查顺序

真遇到慢查询，我现在的顺序是：

1. `EXPLAIN` 看 `type`、`key`、`key_len`、`rows` 四个字段
2. 如果 `type` 是 `ALL`，看是不是上面六种情况之一
3. 如果 `type` 正常但 `rows` 很大，看统计信息和数据分布
4. 如果都正常还是慢，看是不是回表太多——考虑覆盖索引

第 4 条经常被忽略。`SELECT *` 会让索引变成「定位 + 回表」两步，回表是随机 I/O。如果只需要几个字段，把它们都放进索引（覆盖索引），可以省掉整个回表过程。

```sql
-- 索引 (status, created_at, id)
-- 这个查询完全在索引里完成，不需要回表
SELECT id, created_at FROM orders
WHERE status = 'paid' AND created_at > '2026-08-01';
```

## 小结

索引失效的判定标准只有一条：**优化器认为走索引不划算，或者根本用不了**。

前者要调统计信息、改查询条件；后者要改写法。分清楚是哪一种，比背「最左前缀」有用得多。
