JDK 21 把虚拟线程转正之后，我看到的讨论大多集中在两个方向：一是「是不是可以不用 Reactor 了」，二是「性能能提升多少」。

第一个问题基本对，第二个问题问错了。

虚拟线程**不提升吞吐上限**。它改变的是「一个阻塞调用要占多少资源」。这两件事经常被混为一谈。

## 平台线程贵在哪

一个平台线程（platform thread）在 Linux 上对应一个内核线程，默认栈大小 1MB 左右（可以用 `-Xss` 调，但不会调到很小）。它的成本体现在三处：

**内存。** 1000 个线程就是约 1GB 的栈空间，还没算堆里的对象。

**调度。** 内核要在这些线程之间做上下文切换，切换本身有成本，而且线程一多，缓存局部性变差。

**创建。** 创建内核线程是系统调用，比创建一个 Java 对象贵几个数量级。

所以传统做法是**线程池**：固定几十个线程，复用它。这个思路在 CPU 密集型任务上完全正确——线程数约等于核数，多了只是互相抢 CPU。

但在 I/O 密集型任务上，线程池就成了瓶颈。一个线程调数据库要等 10ms，这 10ms 里它什么也不干，却占着一个池位。并发上去了，池子被打满，后来的请求只能排队。

于是有了异步编程：CompletableFuture、Reactor、协程。本质都是**把「等待」从线程里拿出来**，让少量线程轮流处理大量等待中的请求。

代价是代码变得难写。一个简单的「查用户 → 查订单 → 拼结果」，异步版本要处理回调嵌套、错误传播、上下文传递。调试栈也变浅了。

## 虚拟线程做了什么

虚拟线程是 JVM 自己调度的线程。它挂载在少量载体线程（carrier thread，也就是平台线程）上，遇到阻塞时自动卸载，等阻塞结束再挂回去。

关键点：**这个卸载是 JVM 自动做的，不需要你写回调。**

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    var futures = urls.stream()
        .map(url -> executor.submit(() -> fetch(url)))
        .toList();
    for (var future : futures) {
        results.add(future.get());
    }
}
```

这段代码对每个 URL 开一个虚拟线程，写法完全是同步的。底层可能是几百个虚拟线程挂在 8 个载体线程上，阻塞时自动让出。

所以虚拟线程的价值是：**用同步的写法，拿到异步的并发度。**

## 它不解决的问题

<Callout type="warning" title="三个常见误解">

**一、CPU 密集型任务不会变快。** 虚拟线程不增加核数。一个 8 核机器上跑 10000 个虚拟线程做矩阵运算，只会比 8 个平台线程更慢——多了调度开销和缓存抖动。

**二、不是所有阻塞都会被卸载。** 只有 JVM 认识阻塞点（网络 I/O、`Thread.sleep`、`LockSupport`、大部分 `java.util.concurrent` 的同步器）才能卸载。如果你在 `synchronized` 块里做阻塞调用，虚拟线程会被**钉在**载体线程上（pinning），卸载不了。这个块就成了瓶颈。

**三、它不会自动修复线程安全问题。** 一千个虚拟线程同时改一个 `HashMap`，照样出问题，而且更难复现。

</Callout>

第二条是最容易踩的。JDK 21 里 `synchronized` 会导致 pinning，JDK 24 才通过 JEP 491 解决了这个问题。所以如果你现在用 21，要么升级，要么把关键路径上的 `synchronized` 换成 `ReentrantLock`。

顺带一提，还有一个更隐蔽的 pinning 来源：`Object.wait()` 和某些 native 方法。排查工具是 JFR 事件 `jdk.VirtualThreadPinned`，打开它就能看到哪些地方被钉住了。

## 线程池还要不要

要。而且分工要清楚：

| 场景 | 用什么 |
| --- | --- |
| CPU 密集（计算、序列化、压缩） | 固定大小平台线程池，大小 ≈ 核数 |
| I/O 密集（HTTP、数据库、消息队列） | 虚拟线程 |
| 有明确并发上限的外部调用 | 信号量 + 虚拟线程 |

第三种容易被忽略。虚拟线程让「开一万个」变得便宜，但这不代表下游能承受一万个并发请求。**你依然需要限流**，只是限流的对象从「线程池大小」变成了「信号量许可数」。

```java
private static final Semaphore DB_PERMITS = new Semaphore(20);

void queryWithLimit() throws InterruptedException {
    DB_PERMITS.acquire();
    try {
        // 这里可以放心阻塞，虚拟线程会卸载
        jdbc.query(...);
    } finally {
        DB_PERMITS.release();
    }
}
```

这个组合的好处是：等待许可的虚拟线程不占资源，而真正的并发被压在数据库能接受的范围内。

## 我的实际选择

这个博客的后端没用到虚拟线程——请求量太小，Spring 默认的 Tomcat 线程池绰绰有余。引入新技术要能回答「解决了我哪个具体问题」，答不上来就不引入。

但如果要写一个爬虫、一个批量同步任务、一个需要同时调几十个下游服务的聚合接口，虚拟线程是我现在会默认选的方案。理由很简单：代码可读性回到了同步的水平，而并发度是异步的水平。

真正需要判断的是——**你的瓶颈到底在等，还是在算。** 在等，虚拟线程有用；在算，它只会让事情变复杂。
