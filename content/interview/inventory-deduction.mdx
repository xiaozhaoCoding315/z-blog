---
question: 库存扣减有哪些方案？怎么防超卖又不影响性能？
category: 系统设计 & 场景
difficulty: 难
tags: [库存, 防超卖]
companies: [阿里, 美团]
---
**三种方案从轻到重**：

**1. 数据库条件更新（小体量首选）**：

```sql
UPDATE stock SET num = num - 1 WHERE sku_id = ? AND num >= 1
```

影响行数 0 = 卖光了。**单行行锁天然防超卖**——简单可靠。瓶颈：同一爆款 SKU 的更新都在一行上排队，**单 SKU 约 500~1000 QPS 到顶**。

**2. Redis 预扣 + 异步落库（秒杀级标配）**：Redis Lua 原子"判断→扣减"，扣成功发 MQ，DB 异步对齐（DB 层再条件更新兜底）。**热点 SKU 的扣减扛到 5 万+ QPS**。要点：Redis 与 DB 之间的短暂不一致靠"预扣额度"业务容忍 + **定时对账**校准。

**3. 库存分桶（天花板方案）**：爆款 SKU 的库存拆成 N 个子桶（bucket_1..N 各 100 件），请求随机路由到某桶扣——**单 key 热点变 N 个**，桶扣光了去别的桶"借"或直接失败。1826 京东抢购就是这思路。

**防超卖的本质**：所有方案殊途同归——**"判断+扣减"必须原子**（DB 靠行锁、Redis 靠 Lua 单线程）。**多买**（一人一单）另算：Redis set / 唯一索引。

**答题结构**：量级确认 → 方案递进 → 每种的天花板与代价 → 对账兜底。
