---
question: 写文件时数据什么时候真正落盘？page cache 的作用？
category: 操作系统
difficulty: 难
tags: [page cache, IO]
---
**你 write() 完数据并没到磁盘——先进了 page cache（页缓存）**，操作系统"记账"说写完了（写回 write back 机制），**真正的落盘由内核异步慢慢刷**（脏页刷盘：定时 30 秒/脏页比例超阈值/内存压力时）。

**为什么这么设计——三头赚**：
- **写飞快**：write 只拷贝到内存就返回（毫秒变微秒）
- **读也飞快**：第二次读同一文件直接命中缓存（磁盘都不用碰）
- **合并优化**：多次小写攒成大块顺序写——磁盘最爱的模式

**代价——丢数据的窗口**：write 返回成功 ≠ 落盘。**断电/宕机，缓存里的脏页蒸发**。数据库最怕这个——所以有各自的应对：

- **MySQL redo log**：`innodb_flush_log_at_trx_commit=1` 时每次事务 fsync 强制刷盘（穿透缓存直写磁盘）——**数据库的持久性就是拿 fsync 换的**
- **Redis AOF everysec**：折中——每秒 fsync 一次，最多丢 1 秒

**三个刷盘 API 的力度**：write（进缓存）→ fdatasync（把我的数据刷下去）/ fsync（数据+元数据都刷）——**面试聊到数据库持久化必回到这里**。

**一句话**："page cache 用'先记账后搬砖'换性能；数据库用 fsync 把关键数据的账当场结清"。
