**RPC（如 Dubbo）调用链拆开看**：

代理层（你调的是个接口，实际是框架生成的代理对象）→ **序列化**（对象→字节，hessian/protobuf）→ **网络传输**（Netty 长连接）→ 服务端反序列化 → 反射调真实实现 → 结果原路返回。

**背后还有两个隐形服务**：注册中心（调用方要找到服务在哪——服务发现）+ 负载均衡（多个提供者挑一个）。

**RPC vs HTTP 对比（高频追问）**：

- **性能**：RPC 二进制序列化（protobuf 体积小 3-5 倍）+ 长连接复用 vs HTTP 文本协议+短连接——**RPC 快是快在设计目标就是内部调用**
- **契约**：RPC 有 IDL/接口定义（强类型，改接口编译期就报错）vs HTTP+JSON 松散（运行时才炸）
- **生态**：HTTP 是宇宙通用语（跨语言跨公司零成本）；RPC 框架绑生态（Dubbo Java 系、gRPC 跨语言但都要生成代码）
- **服务治理**：RPC 框架自带注册发现/负载均衡/熔断；裸 HTTP 要自己搭（或上 Service Mesh）

**现代趋势**：内部 RPC 化（gRPC/Dubbo3）、对外 HTTP/REST 化——**对内效率对外通用**；Service Mesh 把治理下沉到边车，RPC 框架回归"纯通信"。

**一句话**：RPC 本质也是网络调用，只是把"对象怎么传、服务怎么找、挂了怎么办"做成了体系化工程。
