**先纠正概念**：TCP 是**字节流**协议，只管把字节按序送到，**根本不知道"消息"边界在哪**——"粘包"不是 TCP 的 bug，是应用层没定义边界却怪人家。

**现象怎么来的**：发送方三次 write 被内核合并成一个段（接收方一次读到两条——粘）；一次 write 太大被拆段（读到半条——拆）。

**四种定界方案**：
1. 固定长度——简单但浪费
2. 分隔符（Redis 协议用换行）——内容要转义
3. **长度前缀（工业标准）**：消息头 4 字节写明 body 长度，先读头再按长读体——HTTP 的 Content-Length、RPC 框架、Netty 都这思路
4. 上层格式配对（JSON 括号）——低效不推荐

**自研协议标配**：magic + version + type + length + body。
