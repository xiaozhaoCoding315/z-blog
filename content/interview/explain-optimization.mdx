**标准四步**：找到它 → 看计划 → 定位原因 → 动手优化。

**第一步怎么找**：慢查询日志（long_query_time 阈值），线上该常开。

**第二步 EXPLAIN，重点盯四个字段**（现场能说出含义就赢一半）：
- **type**：访问方式。好到差：const → ref → range → index → **ALL（全表扫描，红灯）**
- **key**：实际用了哪个索引（和你建的不一定是同一个——优化器自己选）
- **rows**：预估扫描行数，10 万级就要警惕
- **Extra**：Using filesort（排序没吃到索引，内存/磁盘排序）、Using temporary（临时表，group by 常见）都是优化信号

**第三步常见病因**——索引失效写法（这段是背诵重点）：

```sql
WHERE YEAR(create_time) = 2024      -- 对列用函数：失效
WHERE phone = 13800138000           -- 列是字符串却传数字：隐式转换失效
WHERE name LIKE '%三'               -- 前导模糊：失效（'三%' 不失效）
WHERE a = 1 OR b = 2                -- b 没索引：整条失效
-- 联合索引 (a,b,c)：查 b+c 不带 a，违反最左前缀：失效
```

**第四步优化手段**：建/改联合索引（区分度高的列放前面）、覆盖索引干掉回表、深分页用游标或延迟关联。

**加分句**："优化器没选我的索引"也是一种病——统计信息过期（ANALYZE TABLE 刷新）或它估算回表成本太高，explain extended 能看到估算过程。
