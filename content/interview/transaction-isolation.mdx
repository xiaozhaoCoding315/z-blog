**四个隔离级别，按"会出什么问题"记**：

| 级别 | 会出的问题 | 大白话 |
| --- | --- | --- |
| 读未提交 | 脏读 | 别人没提交的草稿你都看得见 |
| 读已提交(RC) | 不可重复读 | 第一次读 100，别人改提交了，第二次读变 80 |
| **可重复读(RR, InnoDB 默认)** | 基本解决幻读 | 同一事务里读多少次都一样 |
| 串行化 | 无 | 排队执行，安全但慢 |

**MVCC 讲成故事**：每行数据背后挂着一条**版本链**（通过隐藏的 roll_pointer 指向 undo log 里的旧版本，像 git 的提交历史）。事务要读某行时，它拿着一张**"可见性名单"（ReadView）**去对：这个版本是谁改的？在名单里"已提交"的范围吗？不可见就顺着链往回找旧版本——**读不阻塞写、写不阻塞读**的魔法全靠这个。

**RC 和 RR 的全部区别就一句话**：RC **每次查询都换一张新名单**（所以能看到别人新提交的）；RR **整个事务只用第一次查询时那张名单**（所以读多少次都一样）。同一套机制，就差换不换名单的时机——把这个说清楚，比背定义高一个段位。

**补一句**：快照读（普通 select）走 MVCC 读旧版；当前读（select for update / update）读最新版并加锁——RR 下幻读就是靠间隙锁在当前读时挡住的。
