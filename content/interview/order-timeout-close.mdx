**方案选型看量级**（延迟通知怎么来——上一题讲过通道，这里讲**订单侧的完整设计**）：

**通知通道**：RocketMQ 延迟消息 / Redis ZSet 轮询 / 定时扫表兜底——**大厂标配是"延迟消息 + 定时扫表双保险"**（MQ 可能丢/延迟，扫表每小时兜一遍超时未处理的漏网之鱼）。

**订单侧的三个关键设计（比通道更重要）**：

**1. 状态机约束关闭的幂等与安全**：

```sql
UPDATE orders SET status = 'CLOSED', close_reason = 'TIMEOUT'
WHERE order_id = ? AND status = 'WAIT_PAY'   -- 影响行数=0 说明已被支付/已关闭
```

**必须带当前状态条件**——用户在第 29 分 59 秒支付了，第 30 分钟的关闭消息到达，条件更新失败自动放弃。**"到点提醒 + 查库裁决"**，永远不信消息的单方面判断。

**2. 关闭要做的连锁动作**：回滚库存（+1）、退优惠券（恢复可用）、退积分——**本身也要幂等**（重复关闭消息重放无害），用状态机或"关闭流水表"唯一约束兜住。

**3. 支付回调与自动关闭的竞态**：两个几乎同时到达——**分布式锁串行化**或都走状态机条件更新（谁先成功谁算）——保证不会"已支付还被关闭""关了还能支付"。

**点睛**："延迟消息只是闹钟，**状态机才是裁判**——所有异步到达的事件，最终都要到数据库状态这一关来裁决"。
