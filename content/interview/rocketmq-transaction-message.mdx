question: RocketMQ 事务消息是怎么实现的？

**要解决的问题**：本地事务（订单落库）和发消息必须"同生共死"——库落了消息没发（下游不知道有新订单）或消息发了库没落（下游空欢喜）。

**RocketMQ 的半消息方案——"先扣半，确认后再投递"**：

1. 生产者发**半消息（half message）**——Broker 收下但**对消费者不可见**（藏在系统 topic 里）
2. 生产者执行**本地事务**（订单落库）
3. 根据本地事务结果 **commit 或 rollback**：commit → 半消息转到正式 topic 消费者可见；rollback → 删除
4. **Broker 没等到确认怎么办（兜底核心）**：定时**回查**生产者"那个事务成没成？"——生产者查订单表状态返回 commit/rollback。**回查兜底 = 挂了也能对账，消息绝不悬空**

**为什么这套能保证一致**：消息发送（半消息）在本地事务**之前**且不投递——本地事务成功才可能被消费；配合消费端幂等 + 重试，整条链路最终一致。

**对比本地消息表**：思想同源（都是"事务结果决定消息命运"），事务消息把"消息表+扫描重发"的脏活挪进了 Broker——业务少建一张表，但要实现回查接口。

**答题点睛**："半消息把'先有鸡还是先有蛋'变成'先下订金再确认'——回查机制是它比双写方案可靠的关键"。
