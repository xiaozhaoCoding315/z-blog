question: 订单状态机怎么设计？为什么所有订单操作都要过状态机？
category: 系统设计 & 场景
difficulty: 中
tags: [状态机, 订单]
companies: [美团, 阿里]

**订单的坑不是字段多，是"不该发生的转移发生了"**：已取消的订单被发货、已退款还被支付回调改状态、并发的关闭和支付打架——**没有状态机约束前，每个 bug 都是"这个状态怎么变成这样了"**。

**设计三步**：

**1. 枚举所有状态与合法转移**：待支付 → 已支付/已关闭；已支付 → 已发货/退款中；退款中 → 已退款/已支付……**画出状态转移表**：哪些转移合法、谁触发（用户/系统/回调）、触发时做什么副作用（回库存、退优惠券）。

**2. 转移的执行——条件更新做守门员**：

```sql
UPDATE orders SET status = 'PAID' WHERE order_id=? AND status='WAIT_PAY'
```

影响行数 0 = 当前状态不允许这个转移（已关闭/已支付）——**数据库层挡住一切非法时序**。并发场景天然串行（行锁）。

**3. 副作用与转移绑定**：状态变更成功才执行副作用（发 MQ、改库存），且副作用**幂等**（重试无害）——"先改状态后做副作用 + 幂等"是铁律。

**工程化加分**：状态机引擎（Spring StateMachine 或自研枚举表驱动）集中管理转移表，**新转移改配置不改散落各处的 if-else**——代码评审时一眼看清谁能动状态。

**一句话**："状态机不是画给文档看的图，是**写进 WHERE 条件里的秩序**"。
