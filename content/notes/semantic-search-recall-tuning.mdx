我的 ⌘K 搜索面板同时做了两件事：本地关键词过滤 + 服务端向量检索。

关键词那部分一直很稳。但向量那部分——**中文短查询基本搜不出东西**。

这篇是排查过程，以及我最后想清楚的方向。

## 现象

搜「部署」，能出来讲 Docker 的文章。这个正常。

搜「上线」，也应该出来同一批（语义上是一回事）。但经常是空的。

搜「怎么把网站搞到服务器上」——这种长一点的句子，反而能搜到。

也就是说：**查询越短，越难召回**。

## 先看代码

```ts title="src/app/api/search/route.ts"
const { embedding } = await embed({ model: embeddingModel, value: q });
const vectorStr = `[${embedding.join(",")}]`;

const rows = await db.execute<SearchRow>(
  sql`SELECT DISTINCT ON (c.post_slug)
        c.post_slug, p.title, c.heading,
        left(c.content, 120) AS snippet,
        1 - (c.embedding <=> ${vectorStr}::vector) AS similarity
      FROM chunks c JOIN posts p ON p.slug = c.post_slug
      ORDER BY c.post_slug, c.embedding <=> ${vectorStr}::vector
      LIMIT 8`
);

return NextResponse.json({
  items: rows
    .filter((row) => row.similarity > 0.3)   // ← 问题在这
    .sort((a, b) => b.similarity - a.similarity)
    .slice(0, 6),
});
```

`similarity > 0.3`，这个 0.3 是我当初随手定的。

## 0.3 到底是什么含义

先搞清楚 `1 - (embedding <=> $1)` 在算什么。

`<=>` 是 pgvector 的**余弦距离**算符。余弦距离 = 1 - 余弦相似度。所以：

```
similarity = 1 - 余弦距离 = 余弦相似度
```

取值范围 -1 到 1，1 表示方向完全一致。

那我为什么定 0.3？**因为我不确定中文 embedding 的相似度分布长什么样，随便挑了个「看起来不会太宽松」的值。**

这是典型的凭感觉调参。我后来打了个日志，把实际分数打出来：

```
查询「部署」
  0.71  用 Docker 把应用部署到云服务器
  0.64  2G 内存服务器 OOM
  0.42  增量同步
  ...

查询「上线」
  0.48  用 Docker 把应用部署到云服务器
  0.39  2G 内存服务器 OOM
  0.31  增量同步
```

看到区别了吗：**同一个语义，长查询的分数普遍比短查询高 0.2 左右**。

「上线」和「部署」在语义上几乎等同，但分数差了一截。短查询的 embedding 向量本身就「不够具体」，在向量空间里落点比较居中，跟谁的距离都不特别近。

<Callout type="warning" title="这就是阈值写死的根本问题">
阈值是绝对的，但**相似度分布会随查询长度、领域、语言变化**。
一个固定的 0.3，对长查询太宽松（召回一堆不相关的），对短查询太严格（该召回的也过滤掉了）。
</Callout>

## 尝试一：直接把阈值降下来

最直接的想法：那降到 0.15 不就行了。

```ts
.filter((row) => row.similarity > 0.15)
```

结果：短查询确实能搜到了。但长查询开始**召回一堆垃圾**。搜「React Server Components 怎么用」，会出来讲 Redis 的文章——分数 0.18，在旧阈值下本来会被拦掉。

治标不治本。问题的本质不是阈值大小，是**用单一指标做二分类**。

## 尝试二：改成相对阈值（top-K）

另一种思路：不要绝对阈值，改成「取最靠前的几个」：

```ts
return NextResponse.json({
  items: rows
    .sort((a, b) => b.similarity - a.similarity)
    .slice(0, 6),   // 只要前 6 个，不管分数
});
```

这个在「一定有相关内容」的场景下更好——比如相关文章推荐，你总能推荐出 3 篇。

但搜索不行。用户搜一个站里根本没有的词（比如「Kubernetes operator」），你硬返回 6 条结果，而且都是错的，这比返回空更糟糕。

**用户需要知道"没搜到"，而不是被喂一堆勉强沾边的东西。**

## 真正的方向：混合检索

想了几轮之后，我认为正确答案是**混合检索（Hybrid Search）**——把关键词匹配和向量检索的分数融合。

理由很直接：这两种方法失败的方式是**互补的**。

| 场景 | 关键词匹配 | 向量检索 |
| --- | --- | --- |
| 搜「Docker」 | ✅ 精确命中 | ✅ 也行 |
| 搜「上线」找「部署」 | ❌ 字面不匹配 | ✅ 这是它的强项 |
| 搜「pgvector」 | ✅ 一定能中 | ⚠️ 罕见词向量质量差 |
| 搜一个站里没有的词 | ✅ 正确返回空 | ❌ 总是返回点东西 |

看最后两行——**关键词在「罕见专有名词」和「确实没有」这两件事上，比向量可靠得多**。

融合的方式通常是加权：

```
final_score = α × keyword_score + (1-α) × vector_score
```

`α` 一般取 0.3~0.7 之间。具体值要拿真实查询调，但重点是**两个信号都在**，而不是二选一。

## 关键词那一路用什么

最土的办法是 SQL 里 `ILIKE`：

```sql
WHERE c.content ILIKE '%' || $1 || '%' OR p.title ILIKE '%' || $1 || '%'
```

够用，但对中文有硬伤：**没有分词，就没有词的概念**。「部署到服务器」搜「服务器」，`ILIKE` 能中；但搜「上线」永远不会中——因为它不知道这两个字组合是一个词。

正经做法是 `pg_trgm` 做三元组相似度，或者上 `zhparser` 做中文分词：

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX ON chunks USING gin (content gin_trgm_ops);

-- 三元组相似度，对拼写变体和部分匹配更宽容
SELECT similarity(content, $1) FROM chunks;
```

`pg_trgm` 的好处是不需要分词词典，直接把字符串切成三元组。对中文这种无空格语言，效果比预想的好——因为它本质上在做「有多少连续子串重合」的判断。

## 另一个忽视的问题：分块大小影响召回

排查时还发现一件事：**分块粒度会直接影响相似度分数**。

我的分块按二级标题切，最长 800 字。问题是有些小节特别长（比如带大段代码的），切完之后语义被稀释了：

```ts title="src/lib/chunk.ts"
const MAX_CHARS = 800;
const OVERLAP = 100;
const MIN_CHARS = 60;
```

一个 800 字的分块，如果里面 600 字是代码，那它的向量基本在描述「这里有一堆 TypeScript 代码」，而不是「这里在讲分块策略」。

后来我把「含代码块的小节」单独标记，让它在检索时的权重低一点——因为代码块的向量对语义搜索贡献很小，甚至有害。

<Callout type="tip" title="一个被忽略的事实">
向量检索的质量上限，是**分块质量**决定的，不是模型决定的。
模型再好，如果分块把一段完整论述切碎了，那检索出来的永远是半截语义。
调模型之前先调分块。
</Callout>

## 现状和打算

老实说这个功能目前还是「能用」状态，离「好用」有距离。我列的改进清单：

1. **混合检索**——`pg_trgm` 关键词分数 + 向量分数加权融合（最优先）
2. **自适应阈值**——按查询长度动态调整，短查询放宽
3. **分块去代码**——代码块不参与 embedding，或降权
4. **查询改写**——短查询先用一次 LLM 扩写成完整句子再向量化

第 4 条成本最高但效果可能最好：把「上线」扩写成「如何把网站部署到服务器上线」，向量的落点立刻明确。代价是每次搜索多一次 LLM 调用，对个人站有点重。

第 1 条我最近就想动手。等做完了再写一篇复盘。

## 小结

这次的教训不是「阈值调错了」，而是：

**我当初根本没验证过阈值是否合理，只是找了个"看起来不会太严格"的数字就上线了。**

任何一个魔法数字，都应该有数据支撑。我当时只要把分数打出来看一眼，就能立刻发现问题——而不是等用户（其实是我自己）搜不到东西才回头查。

现在我的做法是：**所有涉及阈值的代码，旁边必须有注释说明这个值是怎么定出来的**。说不出来，就说明还没想清楚。
